# AI Testing Plan — Verification Guide
**Version:** 1.0.0 | **Last Updated:** 2026-07-02  
**Target Workspace:** `ai/`

---

## 1. Automated Testing (Unit Tests)

We use **Vitest** for running our unit and integration tests. The test runner handles environment variables automatically by providing mock values during `test` mode, ensuring tests can run offline or in CI/CD without active provider keys.

### 1.1 Running Tests
To execute the automated test suite, navigate to the `ai/` directory and run:

```bash
cd ai/
npm run test
```

### 1.2 Existing Test Coverage
We have implemented 10 core unit tests:
1. **SafetyGuard Tests (`ai/tests/safety.test.js`):**
   * Verifies standard safe prompts are allowed.
   * Blocks prompts missing tenant context (`organizationId`).
   * Blocks prompt injection scripts attempting to override instructions.
   * Blocks jailbreak patterns.
   * Redacts sensitive user PII (SSN, Passwords, cards) dynamically.
2. **ToolManager Tests (`ai/tests/tools.test.js`):**
   * Verifies dynamic tool registry structures.
   * Enforces user permission filtering for LLM definitions.
   * Enforces input argument validation using Zod schemas.
   * Block tool execution when user lacks the matching RBAC permission.

## 2. Manual Integration Testing

To perform end-to-end testing, you can spin up the server locally and query the REST endpoints using `cURL` or Postman.

### 2.1 Boot the Server
First, create your `.env` file and supply active Gemini, Groq, or OpenRouter API keys. Then start the development server:

```bash
cd ai/
cp .env.example .env
# Edit .env with your keys
npm run dev
```

### 2.2 Health Check Validation
Verify the server is running and healthy:

```bash
curl http://localhost:8001/health
```
**Expected Response:**
```json
{
  "status": "ok",
  "service": "nexusops-ai-platform",
  "version": "1.0.0",
  "uptime": 12.34,
  "tools": 42,
  "providers": ["gemini", "groq", "openrouter"]
}
```

### 2.3 SSE Streaming Chat Test (POST)
To simulate the React UI calling the streaming endpoint, make a request using an access token.

> [!NOTE]
> Since we use standard JWT authentication, you will need a valid JWT access token generated by the Express backend (`backend/`) login flow to authorize requests.

```bash
curl -N -X POST http://localhost:8001/api/v1/ai/chat \
  -H "Authorization: Bearer YOUR_VALID_BACKEND_JWT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "userPrompt": "Show me my profile info",
    "sessionId": "test-session-123",
    "clientContext": {
      "currentModule": "AUTH"
    }
  }'
```
**Expected Output (Streamed EventSource format):**
```
event: session
data: {"sessionId":"test-session-123","timestamp":1720000000000}

event: token
data: {"content":"Let me get your profile.","correlationId":"corr_abc123"}

event: tool_start
data: {"name":"getMyProfile","args":{},"correlationId":"corr_abc123"}

event: tool_result
data: {"name":"getMyProfile","result":{"success":true,"data":{"userId":"...","email":"..."}},"correlationId":"corr_abc123"}

event: token
data: {"content":" Done! Your profile lists you as...","correlationId":"corr_abc123"}

event: done
data: {"correlationId":"corr_abc123","usage":{"inputTokens":124,"outputTokens":45},"toolsInvoked":[{"name":"getMyProfile","status":"SUCCESS","executionTimeMs":210}]}
```

### 2.4 MCP Discovery Test
Test the Model Context Protocol endpoint for external agents:

```bash
curl -X GET http://localhost:8001/api/v1/mcp/tools \
  -H "Authorization: Bearer YOUR_VALID_BACKEND_JWT_TOKEN"
```
**Expected Response:**
List of all 42 available tools formatted as JSON schema schemas matching the user's JWT permission claims.

## 3. Mocking Strategy (Offline Testing)

To test the AI Platform without running the backend API:
1. The **ToolExecutor** intercepts HTTP requests and reports detailed logging.
2. In unit test suites, you can spy on the `ToolExecutor.request` method using Vitest mocks to return mocked backend database responses.
3. This allows full validation of LLM tool selection and data mapping entirely offline.
